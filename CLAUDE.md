# Полигон-7 — памятка для Claude Code

Браузерный 3D-шутер от первого лица «Полигон-7». Автор — Кирилл (он не программист-профи, описывает задачи по-русски, разговорно, с опечатками — понимай по смыслу). Игра выкладывается на GitHub Pages из этого репозитория.

## Как работать с Кириллом
- Отвечай **по-русски**, коротко: что изменилось, что проверить. Без длинных технических отчётов.
- Он сам проверяет игру в браузере и пишет, что не так. Делай изменения сразу, не спрашивай лишнего.
- Каждая итерация = новая «версия N». Последняя сделанная — **Version 80** (NET_VER `p7-coop-46`).
- Правь `index.html` в репозитории. **Пока Кирилл коммитит сам**: готовую игру (`index.html`) и обновлённый `CLAUDE.md` отправляй ему файлами в чат, в git не коммить, пока он не попросит.

## Устройство проекта
- **Весь проект — один файл `index.html`** (~14 000 строк, ~2 МБ): HTML + CSS + один большой `<script>` (всё внутри одной IIFE `(() => { ... })();`). Сборки нет, зависимостей нет — всё с CDN:
  - three.js **r128** (cdnjs) — не обновлять, API r128;
  - PeerJS 1.5.4 (jsdelivr) — мультиплеер P2P, грузится по требованию;
  - Firebase compat 12.19.0 (Auth + Realtime Database) — аккаунты, облачное сохранение, таблица лидеров, грузится по требованию.
- Файл огромный: **не читай целиком**. Ищи через grep по именам функций/строк и правь точечно (Edit с уникальным контекстом). Строки очень длинные — многие функции записаны в одну строку.
- Проверка синтаксиса после правок: вытащить содержимое `<script>` и прогнать `node --check` (или `new Function(code)`).

## Главные системы (имена для grep)
- **Режимы**: `mode` = `waves` (волны), `descent` (спуск по подземельям), `roofs`, `pvp`, `tutorial`. Карты — `MAPS`, `buildMap`, `MAP_ORDER`, `DEPTHS`.
- **Игрок/оружие**: `player`, `updatePlayer`, `WEAPONS` (+ `WI` индекс по ключу), `wstate`, `equip`, `SHIELDS`, `SPELLS`, `PETS`, `UPGRADES`, цены апгрейдов `wupCost`, `UP_COST`.
- **Сохранение**: `save` в localStorage `'poligon7-save'` (`SAVE_KEY`), настройки `'poligon7-settings'`, `persist()`. Загрузчик сохранения проверяет каждое поле (`dtherm: s.dtherm && typeof ... ? ... : {}` и т.п.) — **новое поле save нужно добавить в загрузчик**, иначе оно пропадёт. Загрузчик выполняется в самом начале скрипта — константы, объявленные ниже (например `LOOK_OPTS`), в нём использовать нельзя.
- **Аккаунты/облако (Firebase)**: `FB_CFG`, `ACC`, `loadAuth`, `accApply`, `accUpload`, профиль `renderProfile`, аватарки `avaSvg`/`avaHTML`, рамки `frameSvg`. Пути RTDB: `users/$uid` (сохранение), `lb/$uid` (лидерборд), `rooms` (комнаты).
- **Уровни/XP**: `lvInfo`, `addXp`, `LV_MAX = 1000`, звания `LV_RANKS`. Рамки и аватарки-награды — каждые 10 уровней до **200** (20 ступеней: `FRAME_N`, `RAVA_N`, цвета `TIER`; 1–10 рисуют `frameSvg`/`avaRewSvg`, 11–20 — `frameSvg2`/`avaRewSvg2`; доступность `lvCap()`). Камуфляжи за уровни (`DCAMO[k].lvl`), монеты за уровень и карточки «Награды за уровни» (`rewTrack`) — только до 100. XP за бой: PvE `kills*2 + bossKills*60 + score/300`, PvP `k*60 + 400 (победа) / 120 (участие)`.
- **Мультиплеер**: хост-авторитарный P2P через PeerJS. `NET`, `MATES`, `netSend`, `netTick`, аватары других игроков `o.av.rig`. Константа **`NET_VER`** — **повышай её (`p7-coop-47`, …) только если меняется сетевой протокол** (формат сообщений/синхронизации); если изменения только локальные/визуальные — не трогай, чтобы люди на старой версии могли играть вместе.
- **PvP**: `PVP`, `PVPC` (настройки комнаты: `br` — разрушаемость, `dr` — дредноуты, `dmap` city/port), `pvpStart`, `pvpRespawn`.
- **Дредноуты** (большие мехи в PvP): `DRD` (состояние), `DTYPES` (5 стандартных: Страж, Инферно, Призрак, Горнило, Бастион), свои сборки `dcList()`/`save.dcus` (sid ≥ 11), модули `DMS`, покупка модулей `dmodPrice`/`dmodOwned`, арсенал `renderArsDread`, покраска `dPaint`/`dSetPaint` (поля `a`, `b`, `g` — цвета, `p` — камуфляж, `k` — комплект, `e`, `n`), комплекты `DKIT`, тепловизор `thermToggle`/`thUseC` (обычный 1500, цветной 4500). **У 5 стандартных дредноутов скинов/покраски нет — только у своих сборок.**

- **Графика**: пост-обработка `POST` (шейдер comp, в т.ч. тепловизор `thm/thg`), камера фона меню `menuCamSafe`.
- **Боец (персонаж игрока)**: `buildRobot(L)` → `humanRobot(...)` (гуманоидное тело). Враги используют `humanoid(...)` — это другая функция, не путать. Анимация: `bendLimbs`, структура рига одинакова (`legL/kneeL/footL`, `torso`, `head`, `armL/foreL` …) — на неё завязаны анимации, оружие (`armAttach`), шлемы и сетевые аватары. Телосложения `HBUILDS`. Опции внешности: `LOOK_OPTS`, `LOOK0`, комплекты `SKIN_SETS`, камуфляжи `DCAMO`/`DPAT`.

Магазинов два на одном экране `shopScr`: `openShop('w')` — **Магазин оружия** (вкладки `guns`, `melee` = ближний бой + магическое оружие, `trophies`, `spells`, `shields`, `pets`, `gear` = снаряжение + улучшения), `openShop('s')` — **Магазин скинов** (`scase` кейсы — первая вкладка, `sfighter` комплекты и бронежилеты бойца, `sdread` комплекты дредноутов, `scamo` камуфляжи и скины дредноутов, `sprof` аватарки и рамки). Режим — `shopMode`, вкладка — `shopTab`/`showShopTab`; у кнопок вкладок `data-m="w|s"`, у блоков `data-sp`. Кнопки меню `shopBtn` / `skinShopBtn` (в одном ряду, `.navpair`). Картинки: оружие `weaponThumb`, щиты `shieldThumb`, помощники `petThumb`, ботинки/ранец `gearThumb` (все через `renderThumb`).
- **Аватарки и рамки профиля**: `avaHTML(a, size, fr)`. Аватарки: `p:N` — обычные (`avaSvg`), `r:N` — за уровни, `b:N` — купленные (`BUY_AVA`, `avaBuySvg`, владение `save.bava`). `c:N` — из кейсов (`CASE_AVA`, `caseAvaSvg`, владение `save.cava`). Рамки (`save.prof.fr`): 1–20 — за уровни, 21–30 — купленные (`BUY_FR`, `frameBuySvg`, владение `save.bfr`, номер = 20 + N), 31–38 — из кейсов (`CASE_FR`, `caseFrameSvg`, `save.cfr`, номер = 30 + N). `myAva`/`myFrame` проверяют доступность; в сети и лидерборде `fr` ограничен 0–40 (`clamp`), в правилах RTDB (`rooms/$code/fr`, `lb/$uid/fr`) тоже должно быть `<= 40`.
- **Кейсы** (Магазин скинов → Кейсы): `CASES` (3 кейса: 5 000 / 10 000 / 50 000, по 17 предметов: 5 гражданских, 4 армейских, 3 тайных, 2 засекреченных, 3 контрабанды — общий шанс контрабанды 0,2 % делится между ними поровну), качества `RAR` (шансы 61,46 / 26,34 / 10 / 2 / 0,2 %), предмет `[t, k]`: `s` — скин (ключ `DCAMO` 60–94, поля `cs` — номер кейса, `rar`, `pt` — узор, `anim` — переливающееся свечение), `a` — аватарка, `r` — рамка; качества аватарок/рамок — `CASE_RAR`. Функции: `cItemRar/cItemName/cItemKind/cItemOwned`, `rollRar`/`rollItem`, `openCase` (деньги и предмет записываются сразу, дубликат — возврат половины цены), рулетка `caseSpin` → `caseResult`, звуки `CSND`. Узоры скинов из кейсов — `caseCamo` (один и тот же порядок случайных чисел для цвета и свечения), переливание контрабанды — `animGlowTex`/`animSkinTick` (общая текстура перекрашивается раз в 70 мс), превью со свечением `caseSkinPrev`. 3D-кейсы: `buildCase`, превью `caseThumb`, отдельный маленький рендерер для вращения `CV`/`caseViewTick`. Скины из кейсов попадают в группу «Из кейсов» (`camoGroups` → 4-я группа) у бойца и в покраске своих дредноутов; плитки подсвечены цветом качества (`rarAttr`).
- **Рулетка кейса**: `caseSpin` (лента 64 плитки, выигрыш — 54-я, плавное торможение 6,5 с, старт после декодирования картинок), `caseStop` → `caseResult`; `crTok` отменяет устаревшие таймеры (`caseClose` его увеличивает). Плитки — `crTile`: контрабанда всегда золотая карточка «?» (`.crsec`), у выигрышной на обороте настоящий предмет, после остановки она переворачивается (`.rev`). Пока открыта рулетка, `frame()` не рендерит 3D-меню (иначе лента дёргается). Блок результата `#crRes` всегда занимает место (без сдвига ленты).
- **Случайные паттерны (экземпляры)**: настройка у скина — `DCAMO[k].vr` из `SKVAR` (сейчас: вся контрабанда 69, 79, 88, 89–94; засекреченные 68, 78, 87; тайный 86 — у остальных фиксированный вид). Палитра может иметь 4-й цвет (используют 89 и 91). Режимы переливания `anim`: `fire`, `nova`/`pulse` (колебание оттенка палитры), `rainbow`, `glitch` (мерцание). `vr.pal` — палитры `[имя, [основной, тёмный, свечение], вес]`, `z` — диапазон масштаба, `rot` — предел поворота. Номер паттерна `s` **1–1 000 000** (`PAT_MAX`; новое выпадение — `patRoll()`, равномерно, через `crypto`) → `skVar(k, s)` (палитра, масштаб, поворот, участок) вычисляется из номера каждый раз, ничего не хранится; формула та же, что при 1–999, поэтому старые номера выглядят как раньше (номер вне диапазона → витринный вид); `s = 0` — витринный вид для не купленных. У каждого скина один большой рисунок 640×640 (`VMASTER[k]`, кэш `vMaster`), экземпляр — окно в нём (`vWindow`, край по горизонтали сглажен для бесшовности), текстуры `varTex(k, s)` (`DTEX['v'+k+'.'+s]`). Переливание контрабанды включается только когда скин надет на 3D-модель (`skinGlowTex` → `ANIM_SK`), превью статичные. Цвета скина — `camCols(k, s)`, имя палитры — `skVarPal`.
- **Инвентарь и экземпляры (основа будущей торговой площадки)**: три разные вещи — вид скина (ключ `DCAMO` `k`), номер паттерна (`s` 1–1 000 000, только у скинов с `vr`, иначе 0 — определяет рисунок и палитру) и **ID экземпляра** (уникальный, постоянный: `invNewId()` = `x` + время + 2×32 бита из `crypto`). `save.inv = { id: { k, s, t — дата получения (мс), o — откуда: 'c1'..'c3' кейс, 'shop', 'old' (перенос) } }` (в загрузчике с проверкой полей), `save.invV` — метка переноса. Помощники: `invAll`, `invGet(id)`, `invHas(k)`, `invOf(k)` (копии вида, старые первыми), `invAdd(k, s, o)` (новая копия; заодно заполняет старые `camoOwn`/`camoInst` для старых версий игры). Владение `camoOwned(k)` = есть копия в `save.inv` или награда за уровень (награды за уровни — не предметы, без ID, привязаны к аккаунту).
  - Кейс: каждый выпавший скин — новая копия (`openCase` → `invAdd`, ID в `CV.resId`), **компенсации за скины нет**, даже при том же паттерне; за повторную аватарку/рамку по-прежнему половина цены. Покупка камуфляжа/скина в магазине тоже создаёт копию (`o: 'shop'`).
  - Выбор копии: у бойца `look.ci` (корпус) / `look.vci` (бронежилет), у сборки дредноута `dpaint[sid].i`; `camPick(k, ci, cs)` находит свою копию (по ID → по паттерну → самую старую; нет копии — скин снимается), `lookSeedFix` (в `applyLook`) и `dPaint` проставляют из копии паттерн `cs`/`s`, который уходит в сеть (другие видят рисунок; в `look` идёт и `ci`, но другим он не нужен). Плитки выбора `camoTiles` — по плитке на каждую копию (бейдж `#паттерн` или `№n`), атрибут `data-ci`.
  - Перенос старых данных `invMigrate()` (один раз, при загрузке): по копии на каждый паттерн из `camoInst` (нет паттерна — фиксированный `1 + k*37 % 999`, как раньше показывалось) и по копии на каждый купленный вид; выбранный вид сохраняется (копия подбирается по паттерну). Метка `invV = 1` едет вместе с сохранением (и в облако), запись идёт прямо в localStorage **без `persist()`** — чтобы старое локальное сохранение не стало «новее» облачного. Синхронизация аккаунта заменяет сохранение целиком (`accApply` + перезагрузка), поэтому копии не дублируются.
  - Страница «Инвентарь» (`data-page="inv"`, вкладки «Профиль | Инвентарь» `.ptabs` на обеих страницах): `renderInv`, разделы `invTab` 's' (скины и камуфляжи — каждая копия отдельной карточкой + награды за уровни), 'a' (аватарки), 'r' (рамки) — только то, что есть у игрока; карточка → подробности справа (`invSel`): большая картинка `invPrev`, редкость, паттерн, палитра, совместимость, дата и источник, где надет сейчас (`invWorn`), ID экземпляра. Кнопок «надеть» нет — только просмотр.

- **Защита от старых версий игры (формат сохранения `SAVE_FV = 2`)**: основное сохранение всегда пишется строкой `{"fv":2,…}` (`saveRaw()` — в localStorage и в облако `users/$uid.s`). Старые версии это поле выбрасывают, а правило RTDB на `users/$uid` (файл правил отдан Кириллу в v80) не даёт перезаписать облачное сохранение, начинающееся с `{"fv":`, сохранением без него — старая вкладка получает ошибку синхронизации и ничего не затирает. Пока правило не применено, защищают клиентские меры:
  - инвентарь (`inv`, список перенесённых пар «вид.паттерн» `ileg`, удалённые ID `igone` — для будущей торговли, выбранные копии `sel`) хранится ещё и в отдельном ключе localStorage **на владельца** `poligon7-inv:<uid|guest>` (`invKey`, `invRead`, `invStoreWrite`), который старые версии не трогают; при загрузке он сливается с основным сохранением и возвращает выбранные копии, если старая версия их выбросила;
  - все копии инвентаря сливаются только по ID (`invUnion`): новые ID добавляются, удалённые (`igone`) не возвращаются, перенесённые старые предметы (`o: 'old'`) — не больше одного на «вид.паттерн»; ID никогда не пересоздаются, одинаковые копии не объединяются;
  - `accApply` (облако новее) сливает облачный инвентарь с хранилищем этого аккаунта на устройстве, а не заменяет его; `accUpload` перед записью читает облако и сливает чужие предметы (другое устройство) — предметы не теряются;
  - `invLegacy(src)` вместо однократной миграции: из старых полей `camoOwn`/`camoInst` (и из того, что старая версия выбила из кейса) создаются предметы только для пар «вид.паттерн», которых ещё не было (`ileg` помнит все когда-либо созданные) — поэтому она безопасно работает при каждой загрузке и синхронизации и не делает копий повторно;
  - импорт сохранения из файла (`applySave`) — явная замена прогресса, инвентарь заменяется целиком.
  - Проверено `t/v80test.js` в scratchpad (облако имитируется подменой `LOBBY.db`).
- **Наложение скинов (triplanar)**: все камуфляжи, скины и узоры на бойце, бронежилете и броне дредноута кладутся не по UV каждой детали, а по положению точки (`triMat(mat, S)` — `onBeforeCompile` заменяет `map_fragment` и `emissivemap_fragment`, `S` — метров на один повтор картинки: боец 0.55, бронежилет 0.4, дредноут 1.6 (скины) / 0.9 (узоры `patTex`)). Координаты — локальные у детали × её масштаб, поэтому рисунок одной плотности на всех деталях, не растягивается и не «плывёт» при движении. Поэтому текстуры должны быть бесшовными в обе стороны (паттерны из `vWindow` сшиваются `vSeam` по горизонтали и вертикали). Со скином ноги бойца тоже в скине (`legMat: cm ? bodyMat : dark`).
- **Запрет перекраски**: если на бойце скин/камуфляж (`look.cam`) или надет комплект (`save.lookPre`), вкладка «Покраска» заблокирована (`paintLock()`, `#paintLock`), а `buildRobot` берёт свечение/руки-ноги/покрытие из скина (`lookEff`; в командном PvP — цвета команды, флаг `tl` из `teamLook`). Личная покраска остаётся в `save.look` и возвращается при снятии. Цвет бронежилета блокируется, если на нём камуфляж. У дредноута при комплекте или скине/камуфляже цвета брони/корпуса/свечения не меняются (`dSetPaint`, `paintT` берёт цвета из `DKIT[k].pal` или скина; личные `a/b/g` не затираются), ручная перекраска камуфляжа (`c1..c3`) убрана.

## Переводы (обязательно)
- Исходный текст интерфейса — **на русском прямо в коде**. Переводы — два словаря в файле: `const I18N_EN = {...}` и `const I18N_DE = {...}` (одной строкой JSON), ключ = **точная русская строка**, значение = перевод. Применяются во время работы (`I18N`, `tr`, `MutationObserver` подменяет текст в DOM).
- **Каждую новую или изменённую русскую строку добавляй в оба словаря** (английский и немецкий). Если меняешь русский текст — старый ключ перестаёт работать, нужен новый.
- Для строк, собираемых из кусков (`«${name}» куплен …`), переводится каждый статичный кусок отдельно.

## Как проверять
- Быстро: синтаксис скрипта (`node --check`).
- Полноценно — Playwright + headless Chromium (`/opt/pw-browsers`, флаги `--use-gl=swiftshader --enable-unsafe-swiftshader`). Весь код внутри IIFE, поэтому в **копию** файла перед последним `})();` вставляется тестовый хук `window.__p7 = s => eval(s);` — через него можно звать `buildRobot`, `wearSet`, рендерить бойца в картинку и т.п. В сам `index.html` хук **не попадает** — `grep -c __p7 index.html` должен быть 0. Тесты и картинки держи в отдельной папке (scratchpad), не коммить мусор в корень.
- В облачной среде CDN (cdnjs/jsdelivr/unpkg) может быть закрыт — three.js r128 берётся из npm (`npm pack three@0.128.0`) и подставляется через `page.route`.
- Для сетевых тестов нужен локальный PeerJS-сервер; `window.P7_PEER = {host, port, path}` переопределяет сервер.

## Осторожно
- Не ломай синхронизацию персонажей онлайн: внешность передаётся как объект `look` и строится у всех через `buildRobot`. Удалённые детали у игроков на старых версиях просто не рисуются (`(HEAD[L.head] || noop)()`).
- Имена в файле легко пересекаются (было: `tpG` уже занято) — перед добавлением новой глобальной функции/константы проверь grep'ом, что имя свободно.
- Кэши геометрии (`gg`) хранят по ключу — **в ключ должны входить все размеры**, иначе разные телосложения получат одну и ту же геометрию.
- Firebase-конфиг (`apiKey` и т.п.) в клиенте — это нормально, безопасность держится на правилах RTDB (каждый пишет только в свои `users/$uid` и `lb/$uid`).
